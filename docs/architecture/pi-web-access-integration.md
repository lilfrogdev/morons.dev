# Pi Web Access integration review

## Durable dispatch implementation

The migration records one selected route per owner/child/tool ordinal before HTTP dispatch, with a query digest, policy sequence, contract revision and a closed pre-dispatch fallback reason. The existing binding remains the allowed-route envelope, not an Exa credential identity. A duplicate invocation is rejected rather than replayed; a committed admission with a lost response is conservatively consumed. This adds audit and lifecycle evidence, not sandboxing or rollback.

Status: search routing, durable admission and success provenance are implemented in the working tree. Offline verification is partial; activation and live compatibility remain unverified.

## Source and scope

The intended reference is [nicobailon/pi-web-access](https://github.com/nicobailon/pi-web-access/tree/192ac1875e3b8f88c78953dbc314949ec9fcaa27), reviewed at commit `192ac1875e3b8f88c78953dbc314949ec9fcaa27`, not `georgebashi/pi-web-fetch`. The owner reports that their latest Pi search batch used OpenAI and Exa. That does not establish whether queries used explicit providers, fan-out, or fallback.

Source observations:

- `gemini-search.ts::search` supports explicit providers, provider lists, all-provider fan-out, configured sequential routing, and automatic routing. Automatic routing prefers OpenAI for a selected Codex model (also when extension context is absent), otherwise Exa precedes OpenAI after any configured SearXNG attempt. Several failure paths continue to another provider.
- `openai-search.ts::runOpenAISearch` uses streamed Responses with hosted `web_search`, requires a search-call observation, and returns answer text and sources. It does not require or return token usage. Its Codex endpoint is `https://chatgpt.com/backend-api/codex/responses`. This is a compatibility difference from Morons, not evidence that Morons' usage validation caused a particular failed request.
- `exa.ts::callExaMcp` POSTs JSON-RPC `tools/call` to `https://mcp.exa.ai/mcp?tools=...` without an API key. It accepts JSON or SSE. Basic search uses `web_search_exa`; filtered search can use `web_search_advanced_exa`. The module also supports a separately keyed Exa API. These are remote search services, not local browser search.
- Exa results can contain structured search JSON or formatted title/URL/text blocks. Local formatting of result excerpts does not itself require an LLM summarization call.
- `extract.ts` uses HTTP fetching and HTML extraction including Mozilla Readability; it also contains many optional specialized and remote routes. Chromium is not a prerequisite for the OpenAI/Exa search path.
- Upstream's permissive response parsing, provider fallbacks, configurable endpoints, credential resolution, and optional browser-cookie access are not suitable to transplant wholesale.

## Proposed Morons boundary

Preserve the current OpenAI executor and all historical Brave/OpenAI decoding. Add only the needed Exa search path; public-page retrieval is outside this integration.

Before enabling Exa:

1. Use automatic routing without provider configuration: prefer OpenAI when the bound ChatGPT identity and current policy permit, otherwise keyless Exa. Bind the permitted routes before root or task dispatch and attribute the actual provider. Remote results, project guidance, and models cannot select endpoints or credentials. Credential-store failures and cancellation are terminal; only definite pre-dispatch credential absence under the bound route may fall back. Policy denial does not authorize fallback. No HTTP status, response parsing failure, timeout, or other post-dispatch failure permits fallback.
2. Persist the selected Exa identity and contract before dispatch for roots and task batches. Do not fabricate an OpenAI credential generation, model receipt, or token usage for Exa. Existing `web_model_bindings` enforce the exact OpenAI model/contract and must remain valid for history.
3. Admit Exa against current server data-use restrictions. Until supported by reviewed evidence, its training and retention policy are unknown and cannot satisfy either restriction. Keyless does not mean private or unlimited.
4. Send only the bounded query and fixed search options to a fixed reviewed HTTPS endpoint, with no Morons credentials, conversation history, or environment-derived endpoint overrides. Disable redirects, bound body/result counts and sizes, and validate JSON-RPC identity, errors, SSE framing, and result URLs.
5. Reuse existing Rust HTTP, cancellation, and output-bound infrastructure. No Node, Chromium, generic MCP client, API-key import, or new dependency is needed merely to call the fixed Exa search tool.
6. Keep uncertain attempts terminal. No implicit retry, advanced-to-basic replay, or OpenAI-to-Exa fallback after dispatch. Recheck current policy immediately before each provider dispatch; unknown Exa policy cannot satisfy either privacy restriction. Exa distinguishes locally rejected request construction and cancellation observed before polling HTTP from uncertain transport, response, and later cancellation failures. Durable admission remains consumed even when this pre-send cancellation prevents HTTP; it never authorizes replay.
7. Present Exa results as attributed source excerpts, not an independently verified synthesized answer. Optional future summarization must bind and account for its actual model separately.

Page retrieval is a separate surface: bounded HTTP fetching, redirects and destination checks, extraction, session-scoped bounded cache, and paged/text-search follow-ups. Do not import Pi's automatic repository cloning, personal browser cookies, video stack, or third-party page-fetch fallbacks as incidental dependencies.

## Verification required before activation

Native dispatch admission must recheck the current ChatGPT credential generation after provider preparation, within the serialized storage-worker operation and before consuming an admission. Replacement or removal before admission fails closed without fallback; changes after admission cannot recall already admitted work. This is lifecycle admission, not isolation from other processes running as the same user.

Admission must independently validate fallback reasons, not trust executor-selected labels. Under the current contract, Exa requires unrestricted data use, which also permits OpenAI: a policy-denial fallback cannot be admitted. Missing-credential fallback requires a zero-generation binding backed by credential absence at binding time; later login does not change that pinned identity.

Deterministic tests must cover JSON and SSE, mismatched RPC identity, malformed/error/empty results, oversized bodies and fields, cancellation, deadline expiry, redirect refusal, terminal uncertainty, data-use denial, root/child identity binding, restart without replay, and unchanged historical decoding. Verify the remaining supervisor lifecycle cases before activation. No live service probes, downloads, or installed-app activation/restarts were used for these checks; isolated lifecycle tests launch test fixtures.

### Success provenance boundary

Schema 39 introduces a separate provenance epoch without rewriting historical binding, admission, or result digests. New bindings require a digest-bound credential-absence observation (including the observed unconfigured credential generation); missing evidence is not interpreted as a never-configured identity. Completed searches are recorded before their result is returned, with exact owner/child/ordinal, query, provider, canonical result and completion sequence. Task success references must reconcile one-to-one with these records and native receipts must match the recorded result. Exa retains no invented model usage. Failed or interrupted searches may have admissions without successes; completed successes remain durable even if the enclosing Task fails. These checks detect inconsistent storage, not coordinated rewriting by processes with database authority. Pre-epoch records retain explicitly weaker historical validation.

### Admission deletion detection

Schema 38 retains a bounded admission count on each web binding, backfilled from existing attempts and incremented in the same transaction as every new admission. Validation compares it with surviving attempts independently of terminal output, so deleting an attempt after dispatch fails closed even for interrupted or generic-error owners. This detects inconsistent local storage, not coordinated rewriting by an attacker with database write access; migration cannot reconstruct evidence already deleted before this invariant existed. Historical binding and admission digests remain unchanged.

## Schema-34 collision compatibility

Released schema34 relaxes run counters; a local schema34–40 lineage instead added search state. Schema41 converges both histories without rewriting historical digests or replaying operations. Migration adds the missing search column before schema35, preserves local search/compaction epochs, and relaxes cumulative run and search counters transactionally. Existing database-only backups remain required; no running profile is opened for integration testing.
